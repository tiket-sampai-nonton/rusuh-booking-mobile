ACCEPTANCE CRITERIA (AC1 — FR-22)
================================================================
- The Success screen RE-VERIFIES the authoritative status (useVerifyPayment →
  getStatus) and renders the order summary ONLY when the status is PAID — it
  never trusts navigation alone (D10.2). A non-PAID (FAILED) status routes to the
  recovery screen (/expired?reason=payment). ✓
- Order summary shows: Order ID (bookingId), Jumlah tiket (ticketCount),
  Total dibayar (minorToIDR(amountMinor)), NIK pembeli (MASKED). ✓
- SECURITY: the buyer NIK is shown MASKED only (maskNik → first 2 + last 2,
  D7.1/D7.5). A test asserts NO 16-digit run renders; the raw NIK never reaches
  this screen (it is recorded masked at hold time via setOrderDetail). ✓
- The order detail is captured at the successful hold (Checkout onSubmit):
  setOrderDetail(maskNik(buyerNik), rows.length) — this wired up the previously
  unused session-store action so the summary has real data. ✓

Clean-Arch: the screen reads the session store (UI handoff state) + re-verifies
through the frozen PaymentRepository port via useVerifyPayment; maskNik is a pure
domain rule; no infrastructure import. The e-ticket QR + download/share is RBT-071.

HONEST NOTE: both native shots show the VERIFYING state ("Menyiapkan tiket…"),
NOT the PAID summary. This is correct and intended: a COLD deep-link carries no
funnel state (no attemptId in the store), so useVerifyPayment cannot confirm PAID
and the screen refuses to reveal any order/ticket/NIK — exactly the security
guarantee (never show ticket details without authoritative verification). The
PAID summary content (orderId / qty / amount / masked NIK, and the FAILED→recovery
redirect) is proven by RNTL (SuccessScreen.test.tsx, 5 cases); simctl/adb expose
no scripted taps to drive the full funnel to a verified PAID state on device.
