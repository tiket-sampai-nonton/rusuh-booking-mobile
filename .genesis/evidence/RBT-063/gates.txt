ACCEPTANCE CRITERIA (AC1 — FR-25, D10.4)
================================================================
- The SNAP success/failed callback (successReturnUrl/failedReturnUrl) no longer
  routes STRAIGHT to /success. resolveWebViewNav now sends a success callback to
  the result GATE /payment-result/[bookingId] (carrying attemptId when known);
  a failed/expired callback goes to /expired. ✓ (verified: PaymentWebViewScreen
  test asserts router.replace("/payment-result/bk-1"), not /success).
- The gate VERIFIES authoritatively via GET /payments/{id}/status (VerifyPayment
  → getStatus) and renders success ONLY when that reports PAID — it NEVER trusts
  the callback (D10.2). classifyPayment: PAID→paid (only success);
  FAILED/EXPIRED→failed; READY/AWAITING_PAYMENT→pending. ✓
- VERIFYING/REVIEW/UNKNOWN-equivalent (non-terminal) → processing screen + a
  backoff poll (computeVerifyRefetchInterval: 1.5s→2.5s→4s→6s→8s, clamped; stops
  on terminal; reduced-motion raises the floor). One poller per attempt, TanStack
  owns the interval and cancels on unmount (NFR-05/06). ✓
- Deadline-passed is reconciled from the SERVER clock (ServerClock.remaining via
  serverTime+paymentExpiresAt), never the device clock: a pending attempt whose
  server deadline has passed routes to /expired. ✓ (resolvePaymentRoute +
  useVerifyPayment tests, incl. the serverTime-absent path).

Clean-Arch: payment-verify is a pure domain rule (no React/RN/Expo/infra); the
VerifyPayment use case is framework-free; TanStack confined to useVerifyPayment;
the screen reaches the backend only through the use case → frozen port.
