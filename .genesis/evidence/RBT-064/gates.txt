================================================================
ACCEPTANCE CRITERIA (AC1 — FR-23)
================================================================
- FAILED + still payable (deadline NOT passed, no not-payable code) → RETRY: the
  recovery screen shows "Coba Bayar Lagi" and routes back to /payment/[bookingId]
  to start a NEW attempt. decideRecovery → {kind:"retry"}. ✓
- BOOKING_NOT_PAYABLE (or BOOKING_EXPIRED / HOLD_EXPIRED), OR the server deadline
  has passed → NO retry; the screen offers the RE-QUEUE path only:
  requeueRoute(payment|hold, eventId) → /waiting/[eventId] ("Antre Lagi"), else
  /browse ("Cari Event Lain"). decideRecovery → {kind:"requeue"}. ✓
- expired(reason=payment): RBT-063's resolvePaymentRoute now routes a FAILED /
  deadline-passed payment to /expired/[bookingId]?reason=payment&bookingId=…&status=…
  so the recovery screen knows WHY and can decide retry vs re-queue. ✓
- The retry decision is driven by the AUTHORITATIVE status + the server-reconciled
  remaining time (never the device clock) + the terminal error code — the UI never
  offers a retry the backend would reject. ✓

Clean-Arch: payment-recovery is a pure domain rule (no React/RN/Expo/infra); the
ExpiredRecovery screen reads params + renders, routing via expo-router; no
infrastructure import. BOOKING_NOT_PAYABLE already in the RBT-013 taxonomy.
