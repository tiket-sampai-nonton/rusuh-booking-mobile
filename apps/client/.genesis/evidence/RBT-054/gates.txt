================================================================
ACCEPTANCE CRITERIA (AC1 — FR-16, FR-25)
================================================================
- POST /bookings with Idempotency-Key → hold: HoldBooking use case mints ONE
  key per action (hold-<sessionId>) via IdempotencyKeys, REUSES it across
  retry/refresh, and CLEARS it on success. A double-submit or retry cannot
  create a second booking (FR-25). useHoldBooking's TanStack mutation is
  retry-safe for the same reason. ✓
- Redirect to payment: on success the screen router.replace(`/payment/<id>`);
  the booking id + amount are recorded in the session store for the payment
  page. ✓
- Error mapping (FR-16): CATEGORY_UNAVAILABLE, BUYER_QUOTA_EXHAUSTED,
  QUANTITY_EXCEEDS_LIMIT, MIXED_CATEGORIES_NOT_ALLOWED,
  ATTENDEE_NIK_DUPLICATE_IN_ORDER (the real contract code names) → typed
  DomainError with a Bahasa userMessage, surfaced in CheckoutBar; NO navigation
  on conflict. Untyped failures map to DEPENDENCY_UNAVAILABLE. ✓

Clean-Arch: HoldBooking is framework-free; TanStack confined to useHoldBooking;
IdempotencyKeys bound at the composition root (both mock + real modes) over the
in-memory store. The 5 new error codes added to the single-source ERROR_SPECS
table (OCP), grounded in the Booking Service OpenAPI contract (3. Booking
Service API.openapi.json), not invented.

MOCK TRIGGERS (deterministic, no BE — RBT-054)
================================================================
MockBookingRepository.hold throws the mapped DomainError for: category id
"SOLD" → CATEGORY_UNAVAILABLE; >1 distinct category → MIXED_CATEGORIES_NOT_ALLOWED;
duplicate resolved NIK → ATTENDEE_NIK_DUPLICATE_IN_ORDER; >3 items →
QUANTITY_EXCEEDS_LIMIT. Same idempotency key → same booking (idempotent).
